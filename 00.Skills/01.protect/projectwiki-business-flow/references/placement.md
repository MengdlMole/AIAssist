# ProjectWikiSpace 落点判断

在规划归属时读取。此处目录是候选判断依据，不构成自动归档许可；必须先取得用户指定位置或明确的自动归档授权。自动归档时结合相关代码仓核对职责与边界，可复用当前任务中实际读取、适用范围明确的代码依据，不能仅凭此表、稿件关键词或 AI 总结决定。此表对应创建 skill 时的空间结构；实际执行仍以目标空间当前 README 与治理约定为准。它帮助判断归属，不要求每条输入都生成下面所有类型的页面。

| 要保留的知识 | 默认位置 | 决策边界 |
|---|---|---|
| 有明确主责领域的完整业务流程、规则和状态 | `02-业务总结/02-业务域/<真实领域>/<业务主题>.md` | 即使跨多个仓库或服务，全文仍归该领域 |
| 多领域共同完成、确实没有自然主责领域的目标 | `02-业务总结/03-跨域场景/<业务主题>.md` | 不能只因输入跨仓就判定跨域；Owner 未定时保持 draft |
| 多领域复用且有独立业务含义的过程/规则 | `02-业务总结/04-共享业务能力/` | 同域复用留在该领域；技术代码复用不等于共享业务能力 |
| 领域术语、状态定义 | 所属领域权威主题页 | 跨域共同定义才放 `02-业务总结/05-术语与指标/`，避免重复词义 |
| 关键入口、类方法、配置、事务与重试机制 | `03-架构设计/06-实现/` | 按稳定服务标识聚合；普通主题可单页，复杂服务才建目录 |
| 独立部署服务的职责和定位 | `03-架构设计/02-服务/` | 构建模块、测试模块、聚合 pom 不自动视为服务 |
| API、消息和交互契约 | `03-架构设计/03-接口与消息/` | 来源不全时只保留已知边界，不补造字段与错误码 |
| SDK、公共库与技术复用机制 | `03-架构设计/04-公共模块/` | 记录来源实际具备的库版本和消费者关系 |
| 仓库职责、模块与源码入口 | `03-架构设计/05-代码仓/` | 不按仓库重新复制一套完整业务流程 |

原始 AI 分析稿不是自动归档到 `99-归档` 的历史知识，也不是 `12-AI辅助` 下的业务正文。已有原稿留在输入位置，二次加工后的正文落在业务/技术所属目录；直接承接对话中的分析结果时，无需先创建原稿文件。

## 需要保留的判断差异

- 假设一份输入描述“申请—校验—路由—发送通知”，但明确说目标归“申请处理”领域：场景保留在该领域；只有机制细节确实值得独立维护时再创建实现页。通知涉及另仓不改变主责领域。
- 假设来源写“消息入队成功即完成”，代码片段只证明入队接口返回成功：正文只能说明提交成功，最终业务完成的确认方式保留未知。不能补写消费成功、重试次数或补偿规则。
- 假设既有 active 页描述版本 1 的行为，新稿描述版本 2：先确认新版本是否适用于该页；可以明确并列适用范围，不能将版本差异直接视为既有事实错误。未确认部署状态时不写“生产已切换”。
- 假设稿件只含某方法的过滤条件，无法看出领域：先检索其服务与既有知识。能解释为已知服务机制时可归实现说明；连服务也无法确认时请求关键定位信息，不虚构业务域。

上述均为说明决策的假设，不可作为真实项目知识入库。
