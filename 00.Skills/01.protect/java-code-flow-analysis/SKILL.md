# Java 代码流程梳理

## 目标与边界

围绕用户关心的一个入口和场景建立可验证的代码心智模型，使读者能够回答：请求或事件从哪里进入、依次经过哪些关键节点、数据如何变化、在哪些条件下分支、何处产生副作用、哪些日志可以确认执行位置与结果，以及哪些结论仍不确定。

- 默认执行只读分析。用户只要求梳理、解释或出文档时，不修改业务代码、不新增日志、不启动依赖外部系统的服务。
- 只梳理与用户意图相关的路径。不要把“找到入口”扩张为全仓库架构盘点，也不要为显得完整而列出每个 getter、DTO 转换或框架内部调用。
- 静态可达不等于运行时必经。Spring 代理、接口多实现、AOP、反射、配置条件和动态路由必须标注解析依据与置信度。
- 不虚构运行结果、日志内容、参数值或调用边。实际代码中不存在但建议补充的日志，只能放入“可观测性缺口”，不能混入“关键日志”。
- 保留仓库现有改动。除用户明确授权实现外，生成的 Markdown 文档是唯一允许的新产物。

## 开始前

1. 读取目标仓库的 `AGENTS.md`、开发规范、架构说明和已有文档模板；检查工作区状态，避免覆盖用户改动。
2. 从用户信息中提取：入口线索、关注场景、分析边界、需要覆盖的成功/失败路径、输出位置。先搜索代码补齐信息，不重复询问已给出的内容。
3. 入口无法唯一定位，或不同业务条件会进入实质不同的流程时，列出候选及差异并请用户选择。可以唯一定位时直接分析。
4. 完整读取 [references/tracing-playbook.md](references/tracing-playbook.md)，按其中的 Java 解析规则、证据模型和关键日志标准执行。
5. 先做低成本侦察并选择下述执行强度。只有选择深度档，或标准档确认单上下文不足时，才完整读取 [references/large-codebase-strategy.md](references/large-codebase-strategy.md)。不要仅因项目很大就自动启用大型项目协议。
6. 需要生成 Markdown 产物时，完整读取 [references/report-template.md](references/report-template.md)，遵守其中的结构、Mermaid 和调用树规范。优先使用仓库已有输出目录；没有约定时写入 `docs/code-flow/<入口标识>-code-flow.md`。用户仅要求对话内说明时，在对话中按同一结构压缩输出。

## 执行强度与经济性门禁

先用入口文件、直接依赖、模块结构和第一跳调用做一次低成本侦察，再选择能满足用户意图的最低强度。将模式和覆盖边界写入结果；用户已明确指定强度时遵从用户。

- **快速档**：用于“快速看一下、解释主流程、帮我定位”等请求。单 agent 追踪主成功路径、直接决定结果的分支、关键副作用和关键日志；不建立完整图账本，不声称调用链完整，优先在对话中简洁输出。
- **标准档（默认）**：用于一般代码走读与交接。覆盖主路径、重要业务分支、异常出口、数据/返回流、事务、异步与外部边界；先由单 agent 完成。只有代码证据显示上下文无法可靠容纳，且存在可独立切分的子图时，才升级到大型项目协议。
- **深度档**：用于用户明确要求“完整调用链/全面审计”，或结果将支撑高风险修改、事故根因、迁移和关键评审。建立节点/边账本，执行混合遍历、反向验证和范围内完整性审计；可在通过协作收益门禁后使用子 agent。

不要用固定节点数替代判断。成本信号包括跨模块范围、关键分支数量、动态绑定、异步/消息边界、需要精确证明的异常路径，以及现有上下文能否容纳证据。深度档的“完整”仍然受用户场景、源码可见性和显式边界约束，不等于展开所有 Java/JDK/框架调用。

经济性只能改变遍历顺序、协作方式、文档详略和是否分阶段交付，不能缩小用户已经明确要求的范围。资源不足时保留 `partial/frontier` 并说明继续方式，不得为了清空队列把范围内节点改标为“范围外”。

### 行为门禁

这些门禁约束可观察结果，而不是要求机械执行冗长步骤：

1. **范围门禁**：未确定入口、场景、终点和执行强度，不开始大规模展开。
2. **证据门禁**：没有调用点、绑定配置或运行证据，不把候选调用写成必经路径。
3. **协作门禁**：没有稳定骨架、互不重叠的子图和统一返回契约，不创建子 agent。
4. **完成门禁**：快速档只能称“主流程梳理”；标准档只能称“关键路径已覆盖”；深度档只有通过 frontier 与未闭合边审计后才能称“声明范围内完整”。
5. **成本门禁**：新增读取、动态验证、子 agent 或文档细节必须能降低遗漏风险、提高证据强度或明显减少总耗时；否则省略。

## 分析流程

### 1. 定位入口并固定范围

用 `rg` 优先搜索 URL、注解、类名、方法名、消息主题、任务名或业务关键词。记录入口的文件、符号、触发方式、输入类型和适用条件，并将用户意图改写成一句可验收的范围声明。

先识别项目模块、构建文件和框架，再解析入口。常见入口包括 HTTP Controller/Filter、RPC provider、MQ listener、scheduler/job、`main`/CLI、测试方法和被外部模块调用的 public API。

### 2. 追踪实际调用与返回路径

从入口逐跳读取调用点与被调符号，不只做文本同名匹配。对每一跳记录：调用者、被调者、传入/返回对象、进入条件、副作用、异常行为、同步/异步边界、事务边界、日志及代码证据。

复杂流程先建立紧凑的节点/边账本并维护待展开队列。只有当前层所有相关调用点都已分类为“已展开、已折叠、边界、范围外或未解析”后，才称该层扫描完整。先完成浅层骨架，再按业务相关性、分支与副作用风险选择子图深挖；不要在第一个 service 分支一路读到底后才回头寻找兄弟分支。

同时追踪两个方向：

- 控制流：入口如何到达 service、domain、repository/client、数据库或外部系统。
- 数据/返回流：来源数据如何经过查询映射、DTO/DO/VO、converter/assembler、聚合与序列化形成结果，或如何写入状态并结束消费。

遇到接口、继承、依赖注入、代理、事件、反射或配置驱动调用时，继续查实现绑定、Bean 声明、条件注解和调用配置。无法唯一解析时保留候选，不擅自选一条。

深度档或升级后的标准档在通过协作门禁时，按大型项目策略将互不重叠的关键子图交给子 agent。主 agent 始终负责范围、规范符号键、全局账本、任务切分、结果去重、冲突裁决和最终完整性；子 agent 返回结构化节点/边增量及证据，不各自撰写互不一致的最终调用链。协作不可用或收益不足时，以相同协议串行执行并使用临时检查点控制上下文。

### 3. 提炼关键节点与分支

保留会改变读者理解或故障定位结论的节点：入口与出口、业务校验/权限、关键分支与状态机、核心领域计算、数据库读写、缓存、事务、锁、RPC/HTTP、消息发送/消费、异步交接、重试/降级和异常映射。

折叠无业务语义的透传层、简单 getter/setter、机械映射和框架内部细节；但若它们改变字段、异常、事务、线程、序列化或路由，则必须保留。主路径、重要备选路径和失败路径分开表达，不把所有分支压成一条线。

### 4. 识别关键日志

扫描当前路径节点附近的 logger 调用、统一异常处理、拦截器/MDC、重试与外部调用包装。按参考中的判定标准，只收录能证明“到达、选择、交接、外部结果、状态变化或失败”的日志。

逐条记录日志级别、模板或稳定关键词、触发条件、关键关联字段、诊断价值和敏感信息风险。日志在公共拦截器或切面产生时，说明它与目标入口的绑定证据。没有关键日志时明确写“未发现”，不要用建议日志填充。

### 5. 建立证据闭环

为流程节点分配稳定编号 `N1`、`N2`……，使 Mermaid、调用树、关键节点表和日志表使用相同编号。每个关键结论都引用文件与符号；行号可获得时使用 `path:line`，生成前重新核对。

证据状态仅使用：

- **代码已证实**：调用点、绑定或配置可直接证明。
- **运行已证实**：有用户提供或本次获授权执行得到的日志、trace 或测试证据。
- **推断**：有代码线索但受动态派发、环境配置或缺失实现影响。
- **未知**：当前仓库与上下文不足以判断。

### 6. 生成并自检文档

按报告模板输出一个自包含 Markdown 文档。内容随范围缩放，但入口、流程图、调用树、关键代码节点、关键日志、分支/异常和未知项不得无故省略；不适用时写清原因。

交付前检查：

- 所有列入主流程的节点都能从入口连续到达，并有代码或运行证据。
- Mermaid、调用树和节点表的编号、顺序与命名一致。
- 调用树展示用户场景的实际路径，不是包结构或类目录树。
- 实际日志与建议日志严格分开；日志模板、级别和关联字段来自真实代码。
- 成功、失败、异步、事务和外部边界没有被图形简化掩盖。
- 推断与未知没有写成确定事实，未读取的代码没有被假装分析。
- 深度档的待展开队列已经清空；标准档未覆盖内容已明确列为范围外；快速档未暗示已经穷尽分支。
- 文档记录仓库路径、commit/工作区状态、分析时间和范围，便于日后判断是否过期。

## 完成标准

所有档位都必须满足：入口已唯一定位，用户关心的主路径可连续还原，所报告的关键节点与关键日志有证据，未知项没有被写成事实。完成表述必须匹配执行强度：快速档为“主流程梳理完成”，标准档为“声明的关键路径覆盖完成”，深度档为“声明范围内完整梳理”。外部实现缺失、动态路由无法解析或运行时配置未知时，可以完成静态分析，但必须在结论和未知项中明确限制。
