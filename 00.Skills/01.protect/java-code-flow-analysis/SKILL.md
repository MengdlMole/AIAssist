# Java 代码流程梳理

## 目标与边界

围绕一个入口和场景回答：业务分几步、为什么这样处理、关键输入如何经过筛选/计算/映射形成结果、代码如何调用、何时选择分支或失败、产生哪些副作用、哪些日志能证明执行阶段，以及哪些结论仍不确定。

- 默认只读；未获授权不修改业务代码、不新增日志、不启动依赖真实外部系统的应用。
- 只分析用户场景。折叠无业务语义的透传、机械映射和框架内部调用，但不得折叠关键分支、计算口径、状态变化、事务、异常、异步或外部边界。
- 静态可达不等于运行时必经。动态绑定、AOP、反射和配置选择必须给出依据与证据状态。
- 不虚构运行结果、日志内容或调用边；建议日志只能放入“可观测性缺口”。
- 这是流程分析，不是通用代码审计；除非用户要求，不扩展调查安全、性能、风格或业务规则优劣。

## 按需读取

1. 每次分析完整读取 [references/tracing-playbook.md](references/tracing-playbook.md)，执行调用边、代码 reference 和关键日志标准。
2. 仅在深度档，或标准档确认单上下文不足时，完整读取 [references/large-codebase-strategy.md](references/large-codebase-strategy.md)。
3. 需要生成 Markdown 文件时，完整读取 [references/report-template.md](references/report-template.md)；仅对话说明时按同一结构压缩输出。

## 范围与执行强度

先读取仓库规范、工作区状态、模块结构、入口及第一跳，形成：`入口 + 场景条件 + 终点 + 关注点`。入口无法唯一定位，或场景会切换到实质不同流程时才询问用户。

- **快速档**：主成功路径、直接决定结果的分支、关键副作用和关键日志；只称“主流程梳理”。
- **标准档（默认）**：主路径、重要分支、异常出口、数据/返回流、事务、异步和外部边界；只称“关键路径已覆盖”。
- **深度档**：用户明确要求完整、结果支撑事故/迁移/高风险修改时，建立图账本、混合遍历并审计完整性。

选择满足意图的最低成本档位。经济性可以改变顺序、协作和文档详略，不能缩小用户范围；资源不足时保留 `partial/frontier`，交付阶段性骨架。

## 行为门禁

1. **范围**：入口、场景、终点和档位未确定，不大规模展开。
2. **证据**：没有调用点、绑定配置或运行证据，不把候选写成必经路径。
3. **横切**：HTTP/RPC/MQ/任务入口先检查会改变可达性或语义的校验、安全、AOP、事务和异常映射，再切业务子图。
4. **协作**：没有稳定骨架、互斥子图、共享节点清单和返回契约，不创建子 agent。
5. **负面结论**：“没有事务/数据库表操作/日志/实现/消费者/异常处理”必须检查接口、实现、父类、注解、配置、AOP、SQL/ORM 和必要映射；多 agent 场景由主 agent 复核。
6. **成本**：新增读取、动态验证或委派必须降低遗漏、增强证据或节省总成本。

## 工作流

1. **定位入口**：用 URL、注解、符号、topic、任务名或业务关键词定位触发方式、输入和业务根节点；横切前置链单列，不展开框架流水线。严格按终点停止：用户只要求“发送/交接”时证明生产端与消费者绑定/入口即可，只有要求“消费结果/最终效果”才展开消费者内部。
2. **建立骨架**：逐层枚举当前节点在场景内的相关直接调用，并扫描方法内的分支、筛选/计算、状态变化和结果组装；全部分类为 `expanded / folded / boundary / out-of-scope / unresolved` 后再推进。只有确认不改变业务语义、上下文或边界的机械透传才能折叠。先完成浅层兄弟分支，再优先深挖状态写入、高扇出、事务、异常、RPC、MQ 和动态绑定子图。
3. **双向追踪**：同时追踪入口到副作用的控制流，以及数据、返回对象、异常和状态如何回到终点；按“发布调用 → destination/routing → 消费者绑定/入口 → 异步内部处理”连接跨线程或跨进程链路，任何缺口标为边界或未知。
4. **提炼业务语义与证据**：从分支、查询条件、状态写入、外部载荷和返回结果等业务汇点反向追踪输入与转换，再向前确认影响；将会改变对象集合、范围、顺序、数值、状态、副作用或异常结果的代码片段提炼为关键业务逻辑。关键节点引用声明位置，调用边引用 callsite；逐条解析数据库操作、关键日志和相关配置，证据状态与依据来源分开。
5. **协作与合并**：复杂且可独立的兄弟子图才委派。主 agent 维护规范符号键、全局账本、冲突裁决、负面结论复核和最终编号。
6. **生成与自检**：先输出面向开发者的业务步骤导读，再输出 Mermaid 时序图、文本调用树和证据表。主 agent 以 `B` 聚合业务步骤、以 `R` 标识关键业务逻辑；代码调用仍使用层级 `N`，横切节点使用 `X`，日志使用 `L`，数据库操作使用 `D`。每个 `N` 在时序图、调用树和节点表使用相同的“动作对象；关键输入/条件 → 结果/影响”说明；内联 `R` 紧邻所属节点展示。各视图的编号和语义必须一致，未知值不得凭经验补全。

运行时当前配置值只能来自开发者明确输入；未提供时写“待开发者填写”。若该值决定实质不同路径，覆盖所有候选并将实际选择标为未知，不得声称调用图已闭合。

## 完成状态

- **阶段性骨架**：仍有 `frontier` 或 `partial`；必须列出剩余数量和最高风险节点。
- **静态范围分析完成**：深度档中 `frontier=0`、`partial=0`，所有相关调用已分类；允许保留有候选、影响和验证方式的 `unresolved`。
- **调用图已闭合**：在上一状态基础上 `unresolved=0`；只有此状态可以声称“声明范围内调用链已完整解析”。

外部源码、反射或运行配置缺失时可以完成静态范围分析，但不能把未知实现写成已闭合调用链。
