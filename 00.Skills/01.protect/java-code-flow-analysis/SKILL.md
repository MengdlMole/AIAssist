# Java 代码流程梳理

## 目标

围绕一个明确的 `入口 + 场景 + 终点`，让开发者快速看懂代码如何完成业务，并让后续 AI 用较少上下文恢复同一流程。

分析可以深入，默认呈现必须克制：调用树负责导航，阶段叙述解释业务过程，关键事实精确定义分支、规则、数据终点和日志；同一事实只详细写一次。

## 输出模式

正式落盘默认生成两个同名文件：

- `<flow>.md`：开发者文档，自包含且可顺序阅读。
- `<flow>.flow.jsonl`：AI Flow Pack，保存可组合的结构化事实。

只有用户要求审计、事故复盘、高风险改造或完整证据时，才增加 `<flow>.evidence.md`。仅在对话中回答时可压缩呈现，不为凑格式创建文件。

分析深度与输出长度分开：`quick / standard（默认）/ deep` 决定调查强度；开发者文档仍优先简洁。

## 按需读取

- 每次分析完整读取 [references/tracing-playbook.md](references/tracing-playbook.md)。
- 生成正式输出时完整读取 [references/report-template.md](references/report-template.md)。
- 仅当调用图明显超出单上下文、需要分阶段检查点或适合委派独立子图时，读取 [references/large-codebase-strategy.md](references/large-codebase-strategy.md)。

## 分析流程

1. **固定范围**：从仓库规范、入口和第一跳确定场景、终点、关注点与版本基线。只有多个合理入口或终点会实质改变分析方向时才询问用户。
2. **建立树骨架**：先逐层枚举场景相关的直接调用和兄弟分支，再按业务重要性深挖；不要一开始沿单链钻到底。
3. **扫描方法内部语义**：识别不一定形成方法调用、但会改变处理对象、范围、顺序、数值、状态、副作用或失败结果的逻辑，记为 `R`，不要虚构调用节点。
4. **闭合跨层链路**：证明接口到实现、SQL、RPC、MQ、异步任务、回调、事务和异常映射。静态可达不等于运行时必经；配置或动态绑定无法确认时保留候选和未知。
5. **追踪关键数据**：按 `来源 → 转换/筛选 → 传递边界 → 可确认终点` 追踪业务主键、状态、金额、时间范围、数量、幂等键和路由字段。`save/send/async` 不是天然终点；继续确认表、Topic、外部接口、响应或明确丢弃。跨仓库或缺少运行配置时停止推断并说明验证方式。
6. **形成事实账本**：为调用、阶段、规则、数据操作、消息、日志、配置和未知分配稳定 ID，再从同一账本生成两份输出。
7. **验证**：核对主路径、重要分支、数据终点、编号、代码 reference 和证据边界；深度档再审计 frontier 与 unresolved。

## 核心约束

- 默认只读。未获授权不改业务代码、不新增日志、不启动依赖真实外部系统的应用。
- 只展开会影响当前场景业务控制、数据、状态、副作用、异常、事务、线程或可观测性的内容；机械映射、无语义 getter 和框架内部调用可折叠。
- 每个展示节点写成：`ID [标签] Class#method — 业务动作；关键条件/输入 → 结果/影响`。禁止只写“处理请求、调用服务、查询数据”。
- 调用树编号按层级：`N1 → N1.1 → N1.1.1`。同一方法从不同调用点或上下文到达时分别编号；递归/回边引用已有编号。
- 方法内关键逻辑用 `R`；数据库/缓存等数据操作用 `D`；消息用 `M`；日志用 `L`；配置用 `C`；未知用 `U`；横切框架节点按需用 `X`。所有事实必须关联承载它的 `N` 或明确边界。
- 数据库结论必须由 SQL、映射、生成契约或运行证据支持；区分逻辑数据源、逻辑库和物理实例。无法确认物理库时明确写未知，不凭表名推断。
- 关键日志必须真实可达且能证明到达、决策、交接、外部结果、状态变化或失败处置之一；写明稳定内容、打印条件、时点、能证明与不能证明的事实、代码位置。建议日志与已有日志分开。
- 完整 reference 使用 `仓库相对路径:行号 · 全限定类#方法(参数类型)`；调用边优先引用 callsite。默认不复制完整方法。
- 不虚构运行结果、当前配置值、调用边、消费者、表名或日志内容。证据状态只使用：`代码已证实 / 运行已证实 / 推断 / 未知`。

## 开发者文档

正文固定以“范围与结论 → 流程概述 → 树形调用链 → 分阶段说明”为主要阅读路径，再按事实存在补充关键规则、数据流与数据操作、日志和未知项。

- 调用树是唯一必需图形。简单同步流程不生成 Mermaid。
- 只有异步、跨系统、回调、重试、并发或事务时序仅靠树难以表达时，才增加业务时序图；图中原始 `#` 写为 `#35;`。
- 阶段说明按业务过程组织，不按 Java 类逐个翻译。每段说明进入条件、输入、处理、数据/状态变化和下一步，通常 3–6 句。
- 树中以 `[R:R1] [DB:D1] [MQ:M1] [LOG:L1] [CFG:C1] [TX] [ASYNC]` 建立索引；详细事实只在对应小节解释一次。
- 不为不存在的事实保留空表；用一句明确结论即可。不要把日志、数据库、配置拆成独立开发者文档。

## AI Flow Pack

JSONL 每行一个对象，使用语义清楚的字段，不使用难懂的单字母私有 DSL。按需记录：`flow / stage / node / edge / crosscut / decision / rule / sink / lineage / log / config / transaction / retry / unknown`。

首条 `flow` 必须记录代码 `baseline`、分析 `scope`、`coverage`、`frontier_count` 和 `unresolved_count`。`coverage` 只用 `main-path / key-paths-covered / static-scope-complete / partial`；仍有未分类 frontier 时必须为 `partial`。这些元数据供宏观流程和开发规划判断能否复用，不能用文档篇幅替代。

- `flow + stage + decision + sink + unknown` 足以提炼宏观流程。
- 代码规划再读取 `node + edge + rule + lineage + reference`。
- 故障分析再读取 `log + transaction + retry` 等事实。
- 一个事实只保存一次，其他记录用 ID 引用；省略空字段，不粘贴源码。
- Flow Pack 与 Markdown 共用 ID、动作语义和证据状态。两者冲突时不得宣称完成。

## 完成标准

交付前确认：

- 主路径从入口连续到用户终点；重要分支说明条件、两侧结果和业务影响。
- 每个展示方法已扫描内部关键逻辑；异步/MQ 仅在用户终点需要时继续追踪消费者结果。
- 关键数据已到达可确认终点，或以 `U` 说明边界、影响和验证方式。
- 数据操作说明目标、操作类型、条件/关键字段、事务/结果影响和证据。
- Markdown 可独立读懂业务；Flow Pack 可独立恢复阶段、节点关系、分支和数据终点。
- 正式输出从本 skill 目录运行：`python3 scripts/report_id_audit.py <flow>.md --flow-pack <flow>.flow.jsonl`。
- 深度档有图账本时再运行本 skill 的 `scripts/graph_audit.py`；存在未分类 frontier 时只能称“阶段性骨架”，不得称完整。
