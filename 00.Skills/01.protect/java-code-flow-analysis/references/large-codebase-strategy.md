# 大型项目的上下文策略

仅在单上下文难以可靠保存调用图，或存在边界清楚且可独立分析的子图时使用。默认策略：

`固定范围 → 浅层 BFS 建骨架 → 按优先级深挖子图 → 反向验证 → 合并审计`

纯 BFS 容易在工具方法和多实现处膨胀；纯 DFS 容易遗漏兄弟分支。这里的“完整”相对于用户场景和明确边界，未知必须被记录而不是被猜测。

## 1. 维护紧凑图账本

上下文不足时在临时目录记录，不把中间文件写入目标仓库：

- `scope`：入口、场景、终点、版本和停止边界；
- `nodes.jsonl`：规范符号、状态、一句话动作和证据；
- `edges.jsonl`：调用点、条件、边类型和证据；
- `frontier.jsonl`：待展开项、优先级和原因；
- `findings/`：独立子图返回。

规范符号使用 `<module>:<fqcn>#<method>(<types>)`。同一方法可共享符号节点，但每个调用点和上下文是独立边；展示编号仅在合并完成后由主分析者分配。

节点状态只用：`discovered / claimed / expanded / partial / folded / boundary / out-of-scope / unresolved`。`partial` 和 `unresolved` 必须说明缺什么。

## 2. 受约束的浅层 BFS

逐层读取当前节点到足以枚举场景相关直接调用、方法内关键语义和主要边界：

1. 为每个调用点登记边并分类。
2. 为方法内分支、计算、状态变化和结果组装登记 `decision/rule`。
3. 当前层全部分类后再推进下一层。
4. 识别出主要业务子图后停止统一 BFS，转为“局部一跳全量发现 + 关键子图深挖”。

优先级由高到低：决定终点或关键分支；写库/状态/幂等；异步/RPC/事务/异常边界；高扇出编排；普通查询和转换。折叠低价值节点不等于跳过其语义扫描。

## 3. 委派条件与契约

只有在协作可用且子图边界清楚、共享代码少、需要读取多处实现、独立结果能降低总上下文成本时才委派。短链、核心逻辑集中或问题主要是一个动态绑定时，单分析者更经济。

委派前由主分析者完成入口骨架、横切预检和共享节点清单。优先委派同层兄弟子图，每波合并后再决定下一波，不按单个方法碎片化任务。

子任务输入只包含：

- 子图根规范符号及入口 reference；
- 祖先路径条件、事务/线程上下文；
- 用户终点与允许停止边界；
- 共享事实和禁止重复范围；
- 返回格式与证据要求。

子任务返回规范 ID 和事实，不分配最终 `N` 编号：节点/边增量、关键规则、数据操作、消息、日志、数据流、frontier、unknown、折叠项与证据。主分析者必须复核边界连接和关键负面结论。

## 4. 反向验证

正向图稳定后从以下汇点反向切片：

- 用户可见返回和异常；
- SQL 条件、写入字段和最终表；
- 状态转换与幂等键；
- RPC/MQ 载荷及消费结果；
- 关键日志中的业务字段。

反向确认每个结果的来源、转换和控制条件，可以发现正向追踪遗漏的方法内逻辑或数据终点。

## 5. 合并与停止

主分析者按规范符号和调用点去重，解决冲突后统一分配 `N/R/D/M/L/C/U`，再生成 Markdown 和 Flow Pack。至少检查：

- 入口到用户终点可达；
- 每个展开节点的相关直接调用已分类；
- 每个重要分支两侧有结果；
- 每个关键数据有终点或未知；
- DB/MQ/RPC 边有目标和证据；
- `frontier` 为空才能称范围分析完成；`unresolved` 为空才能称调用图闭合。

可用 `scripts/graph_audit.py` 合并和检查 JSON 图碎片。资源不足时保留 `partial/frontier` 并交付阶段性骨架，不能把尚未分析的范围误标为范围外。
