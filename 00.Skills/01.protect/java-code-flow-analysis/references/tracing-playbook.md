## 1. 范围模型

开始追踪前形成四元组：

`入口 + 场景条件 + 期望终点 + 关注点`

示例：`POST /orders + 库存充足 + 订单落库并返回 orderId + 关注幂等、事务与失败日志`。

范围不完整时，先用代码确认默认含义。只有入口有多个合理候选、终点决定追踪方向，或场景条件会切换到不同实现时才询问用户。将未覆盖的分支写入范围外，不以“可能相关”为由无限追踪。

## 2. Java 项目快速定位

### 项目与模块

先看 `pom.xml`、`build.gradle[.kts]`、`settings.gradle[.kts]`、模块目录、README 与配置文件，确认目标类所属模块及跨模块依赖。忽略 `target/`、`build/`、生成代码和 vendored 依赖，除非运行时实际使用的实现只存在其中。

优先使用 `rg`，典型搜索线索：

- HTTP：`@RequestMapping`、`@GetMapping`、`@PostMapping`、Servlet/Filter、WebFlux router。
- RPC：Dubbo/gRPC/Spring HTTP interface 的服务注解、接口实现与注册配置。
- 消息：`@KafkaListener`、`@RabbitListener`、RocketMQ listener、topic/tag 常量、consumer 配置。
- 任务：`@Scheduled`、Quartz Job、XXL-JOB handler、Spring Batch job/step。
- CLI/启动：`main(`、`CommandLineRunner`、`ApplicationRunner`、picocli command。
- 普通方法：符号名、接口声明、实现类、构造注入字段和调用点。

### 先读契约，再读实现

对每一跳优先确认方法签名、参数/返回类型、接口和注解，再读取实现与调用点。类型、接口、schema 和配置比同名文本更能证明真实绑定。

## 3. 调用边解析

### 直接调用

读取调用表达式和目标声明。重载方法必须按参数类型或编译上下文区分；禁止只凭方法名建立调用边。

### Spring 依赖注入与多实现

按以下证据解析实现：构造器参数类型 -> `@Qualifier`/`@Resource(name)` -> `@Primary` -> `@Bean` 方法 -> `@Profile`/`@Conditional*` -> 配置属性。存在多个仍可生效的实现时列为候选分支，标为“推断”或“未知运行时选择”。

### AOP、代理与框架拦截

检查会改变行为的 `@Transactional`、`@Async`、`@Cacheable`、`@Retryable`、权限/幂等/审计注解及匹配它们的 aspect、filter、interceptor。只在 pointcut、注册配置或框架约定确实覆盖入口时加入流程。区分业务方法体与代理附加行为。

### 数据访问

- MyBatis：Mapper 接口 -> XML namespace/statement id 或注解 SQL -> 动态 SQL 分支 -> `resultMap`/别名 -> DO/DTO。复用 SQL 片段和拦截器可能改变最终 SQL，要明确说明。
- JPA：Repository 方法 -> 派生查询/`@Query`/Specification -> entity 映射。不要把方法名猜测当作已验证 SQL。
- JDBC/jOOQ：追踪 SQL 构造、绑定参数、结果映射和事务来源。

区分读、写、条件更新、批量、锁与事务传播。数据库是关键边界，通常不需要继续追踪驱动内部。

### 外部调用

Feign、RestTemplate、WebClient、gRPC、Dubbo 等调用需要确认 client 接口、endpoint/service 标识、请求/响应类型、超时、重试、fallback 和异常映射。到达仓库外契约即停止；没有对端源码时不要描述对端内部实现。

### 异步、事件与消息

将 `@Async`、Executor、CompletableFuture、Reactor、事件发布、MQ producer/consumer 视为边界：记录提交端、载荷、关联键、线程/事务变化和消费端绑定证据。无法证明生产者和消费者使用同一 topic/event 类型时，不连接两端。

### 反射与动态路由

对 SPI、反射、脚本、规则引擎、字符串 Bean 名、策略 Map 和配置路由，记录选择键、候选实现、默认实现及配置来源。除非运行配置可见，否则不要宣布某候选必定执行。

### 返回与异常

调用链不只向下。继续追踪返回对象组装、converter/MapStruct、异常捕获与重新抛出、全局异常处理、HTTP/RPC 状态映射、事务回滚规则。对消息入口则追踪 ack/nack、重试和死信行为。

## 4. 关键节点判定

一个节点满足以下任一条件时通常是关键节点：

- 确定入口、出口或跨模块/跨进程边界。
- 执行业务校验、权限、幂等、去重或关键分支选择。
- 改变核心业务对象、状态或返回语义。
- 发生数据库写入、关键查询、缓存读写、锁或事务边界变化。
- 调用外部服务、发布/消费消息、提交异步任务。
- 执行重试、降级、补偿、异常转换或错误响应。
- 提供诊断主线所需的关键日志。

一个节点若只是无条件透传且不改变数据、控制、线程、事务、异常或可观测性，可折叠到父节点说明中。

关键节点表应记录：节点编号、文件与符号、角色、进入条件、输入/输出、状态或副作用、关键调用、证据状态。代码片段只截取支撑结论的最小范围，优先链接文件与符号，避免复制整段实现。

## 5. 关键日志判定

### 定义

关键日志是能够显著帮助以下至少一个任务的现有日志：

1. 判断一次业务执行是否到达某个关键阶段。
2. 识别选择了哪个关键分支、策略、实现或降级路径。
3. 关联同步与异步、生产与消费、服务与外部调用的同一次业务执行。
4. 确认外部 I/O、数据库写入或状态迁移的结果与耗时。
5. 定位失败阶段、异常类型、重试次数或最终处置。

若删除该日志会明显降低还原执行路径、区分故障原因或证明结果的能力，它通常是关键日志。

### 优先收录

- 入口/出口日志，包含 traceId、requestId、业务主键或任务实例 ID。
- 权限、幂等、规则命中、路由、状态机转换等关键决策日志。
- RPC/HTTP/MQ/异步交接日志，包含对端/主题、关联键、结果码、重试或耗时。
- 数据写入、提交、回滚、补偿和最终业务结果日志。
- catch、统一异常处理、fallback、死信或放弃重试日志。

### 通常不收录

- 仅打印“enter method”且没有阶段意义或关联字段的流水账。
- getter、机械映射、循环逐项 debug 等高噪声日志。
- 不在目标可达路径上的同名日志。
- 框架启动日志，除非用户关注启动流程或它能证明关键绑定。
- 完整 token、密码、身份证号、银行卡号、未脱敏请求体等敏感内容。发现时标风险，不在文档复制实际值。

### 记录方式

从 logger 调用中原样记录日志级别和模板的稳定部分；变量用占位含义表达，不伪造样例值。每条日志写明：所在节点、文件与符号、级别、稳定关键词/模板、触发条件、关联字段、诊断作用、敏感风险、证据状态。

区分三类内容：

- **代码中的关键日志**：在目标路径上有明确 logger 调用。
- **框架/切面日志**：有注册或 pointcut 证据能覆盖目标路径。
- **可观测性缺口**：当前没有足够日志。仅当用户关注日志完备性时提出建议，使用建议字段而非虚构日志模板。

日志级别本身不决定关键性。高频 INFO 可能无关，携带最终失败原因的 WARN 可能关键；DEBUG 日志在排障场景也可能关键。

## 6. 动态验证与停止条件

默认以静态分析产出，并明确其局限。只有用户授权或项目现有测试能安全、局部地验证目标流程时，才运行测试或采集运行证据。不要为了“证明调用链”自动启动依赖数据库、消息系统或真实外部服务的应用。

动态证据可以提升以下结论：实际实现选择、分支命中、AOP 顺序、异步消费、事务/重试结果。记录命令、环境、输入和观察结果；一次运行没有出现某分支，不能证明该分支不可达。

在以下位置停止继续深入：

- 到达用户指定终点。
- 到达数据库、缓存、消息中间件或仓库外服务边界，且内部不在分析范围。
- 后续仅是框架/第三方库内部实现，与用户关注点无关。
- 缺少源码或运行时配置；将缺口列为未知项并说明影响。
