# Java 流程追踪规则

## 1. 固定范围

开始前形成：`入口 + 场景条件 + 终点 + 关注点 + 版本基线`。入口从 URL、注解、符号、Topic、任务名或业务关键词定位。终点应区分“发起调用、完成交接、消费者入口、业务结果”；只追到用户需要的终点，未覆盖内容标为范围外、边界或未知。

## 2. 解析真实调用关系

从调用表达式逐跳读取声明、实现、调用点和必要配置，不能只凭同名文本连边。

- **多实现/重载**：结合参数类型、注入点、`@Qualifier`、`@Primary`、`@Bean`、profile、condition 和配置。不能唯一确定时列候选与缺失证据。
- **AOP/框架分派**：只接入真正覆盖当前入口并改变校验、身份、事务、缓存、重试、异步或异常语义的节点，用 `X` 表示，不伪装成普通调用。
- **数据库**：追到 Mapper/Repository 及 SQL 或映射。实体名和 Repository 方法名不能单独证明表名。
- **RPC/HTTP**：记录目标服务/接口、关键请求与响应、超时、重试、fallback 和异常映射；没有对端源码时停在仓库边界。
- **MQ/异步**：证明发布调用、载荷、destination/routing、消费者绑定、监听入口和内部处理。发布与消费用异步边连接；不能证明绑定一致时列候选。
- **返回/异常**：追踪结果组装、异常捕获/转换、全局处理和回滚；消息消费按需追踪 ack、重试和死信。

每个相关直接调用分类为 `expanded / folded / boundary / out-of-scope / unresolved`。循环记录回边，不重复展开。只有确认不改变业务语义、控制、数据、事务、线程、异常或可观测性时才可折叠。

## 3. 同时检查方法内逻辑

完整性包含两部分：方法之间的因果链连续，方法内部的重要语义没有遗漏。扫描每个展示方法中的：

- 校验、规范化和提前返回；
- 分支条件及条件值来源；
- 过滤、排序、去重、聚合、分批和截断；
- 时间窗口、金额、费率、精度和舍入；
- 状态转换、幂等、锁、事务与结果组装；
- SQL 条件与写入值、RPC/MQ 载荷和异常转换。

改变处理对象、范围、顺序、数值、状态、副作用或失败结果的连续逻辑合并为一个业务规则 `R`。每个 `R` 写明：目的、关联节点、条件、输入及来源、处理公式/顺序、输出、边界、业务影响和 reference。

例如复合值 `7,30` 不能只列配置值；应根据源码说明两个分量的业务含义、`start/end` 计算、时区与开闭区间，以及它如何改变查询或处理范围。

## 4. 关键数据闭环

只追踪影响业务的字段：业务主键、关联键、状态、金额、时间、数量、幂等键、路由键和决定分支的参数。

对每项形成：`来源 → 转换/默认/筛选 → 中间载体 → 传递边界 → 可确认终点`。

- DTO、Command、Entity 和 Event 是载体，不自动视为终点。
- `save/send/submit/async` 是动作，不自动视为终点。
- 终点可以是数据库/缓存/索引/文件、消息 Topic、外部接口、返回值或明确丢弃。
- 当前仓库能找到消费者或回调且用户终点需要消费结果时继续追踪；跨仓库或缺少运行配置时写明当前可确认边界、影响和验证方式。

## 5. 数据操作

操作类型使用 `SELECT / SELECT_LOCK / INSERT / UPDATE / DELETE / UPSERT / MERGE / CALL`；缓存、搜索索引、文件等使用其真实动作。软删除按实际 SQL 记为 `UPDATE`。

每个关键操作记录：

- `D-ID`、关联节点和业务目的；
- 逻辑数据源、可确认的库/schema、表或目标；
- 操作类型、发生条件、查询/更新范围；
- 主键、关联键、状态等关键字段及来源；
- 事务归属、结果影响和失败行为；
- SQL/映射 reference 与证据状态。

一条 SQL 涉及多表时按表分别说明角色。动态表、分片路由、存储过程内部表或物理实例无法确认时写 `unresolved`，不能推断。读取也要说明结果如何进入后续分支、消息、写入或响应。

## 6. 关键分支、配置与边界

关键分支必须写：业务问题、代码条件、条件值来源、求值顺序、命中结果、未命中/default 结果、双方副作用和证据。没有后续调用时使用 `result:<结果>` 或 `boundary:<边界>`。

只记录会改变可达性、实现选择、处理范围、计算口径、重试/降级、异步交接或最终结果的配置。记录完整 key、值格式、作用、证实的默认值、关联 `N/R` 和读取 reference。当前运行值只能写用户提供值或“待开发者确认”；仓库默认值和环境变量占位符不能冒充当前值。

事务、线程、异步、消息、RPC 和仓库外实现都是语义边界；说明切换点、失败影响、重试/回滚/ack 等行为。框架注解只证明声明，不证明某次运行已经提交或完成外部副作用。

## 7. 关键日志

现有日志同时满足以下条件才收录：路径可达；能证明到达、决策、交接、外部结果、状态变化或失败处置之一；没有被同阶段信息更完整的日志无损替代。日志级别不决定关键性。

每条 `L` 必须包含：

- 稳定日志模板和变量含义；
- 代码位置与关联 `N/X/边界`；
- 代码分支及已知运行打印条件；
- `before / after-return / after-commit / on-exception / finally` 时点和相对对象；
- 能证明什么、不能证明什么；
- 业务主键/traceId 等关联字段、来源和级别。

调用前日志只证明准备执行；方法返回后日志不自动证明事务提交、远端业务完成或消费成功；生产者与消费者日志分别证明各自阶段。没有符合条件的日志时直接说明。只有用户关注可观测性时才另列建议日志，并避免复制敏感数据。

## 8. 代码证据与停止

完整 reference：`仓库相对路径:行号 · 全限定类#方法(参数类型)`。XML/SQL 使用 `path:line · namespace.statementId`；调用关系引用实际 callsite。生成或框架代理实现不可见时记录声明、绑定配置、调用点和 `implementation unavailable`。

默认静态分析。只有用户授权且现有测试能安全、局部验证时才运行。到达用户终点、仓库/中间件边界或证据缺失处停止；未知不等于失败，但必须说明它影响什么以及如何验证。
