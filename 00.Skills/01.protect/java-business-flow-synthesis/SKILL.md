# Java 宏观业务流程提炼

## 目标与边界

把多个已分析子流程提炼为开发者容易理解、后续 AI 可以稳定引用的宏观阶段、交接、状态和不变量。

- 默认只读，不修改代码或设计改造方案。
- 代码调用、共享主键或时间先后都不能单独证明业务关系。
- 宏观层只保留业务阶段和必要边界；方法、SQL、详细日志留在子流程产物中。
- Markdown 面向开发者，JSON 契约面向后续 skill；两者从同一事实生成。

## 启动门禁

正式串联前必须有开发者输入：`业务目标 + 起点 + 终点 + 纳入的 flow_id + 至少一个已知关系，或允许提出候选关系`。自然语言即可。

输入不足时只盘点 Flow Pack、列候选关系和少量聚焦问题，状态保持 `waiting-for-developer-input`；不分配最终 `M/H` 编号，不输出可冻结流程，也不从沉默推断批准。

## 输入与按需加载

主要输入是 `java-code-flow-analysis` 生成的 `.flow.jsonl`。先只读取 `flow / stage / decision / sink / lineage / unknown`；只有交接或语义存在歧义时才读取 `node / edge / rule` 或开发者 Markdown，通常不读取日志。

生成文件前完整读取 [references/output-standard.md](references/output-standard.md)。

## 编号与证据

- 宏观节点使用层级编号：`M1` 为端到端根，`M1.1` 为阶段，`M1.1.1` 为必要的子阶段；默认不超过三层。
- 交接使用 `H1...`。子流程事实使用命名空间引用，如 `order-create/S1`、`order-create/M1`、`order-create/D1`、`order-create/N1.2`。
- 证据状态只用 `code-confirmed / developer-confirmed / both-confirmed / inferred / unresolved`。
- 代码现状与开发者业务意图冲突时并列记录，不互相覆盖。
- 先稳定阶段树和交接，再统一编号；协作者不得分配全局 `M/H`。

## 工作流

1. **规范化 brief**：记录目标、起止、范围、来源流程、已知关系及允许 AI 提议的范围。
2. **盘点来源**：校验每个 Flow Pack 的 `flow_id`、基线、覆盖状态、终点和未知；不把不同基线静默混合。
3. **提取宏观卡片**：为每个子流程提取触发、前置、业务阶段、结果、数据终点、状态、交接、关联键和失败出口。
4. **提出候选链**：只有显式调用、API、消息绑定、状态转换或开发者输入才能支撑交接；其余标为候选或未知。
5. **开发者裁决**：只确认无法从代码证明、会改变主干或异常终点的关系；代码已明确的细节不逐项审批。
6. **提炼与追溯**：生成同一组 `M/H` 的分层树、阶段说明、关键交接、不变量和类型化 Flow Pack 引用。
7. **评审与冻结**：开发者明确批准后才设为 `frozen`。冻结时入口必须有向到达所有关键终点，每个关键阶段位于有效路径，关键交接已确认，阻塞未知为零。

冻结不是永久不变；修订时创建新版本，旧版本标为 `superseded`，不静默覆盖。

## 开发者参与

- **启动确认（必须）**：目标、范围、起止和来源流程。
- **关系裁决（按需）**：人工步骤、跨仓库未知、补偿/终止、多候选后继等歧义。
- **冻结批准（必须）**：确认宏观阶段、关键交接、终点和阻塞未知。

## 输出与经济性

默认只生成：

- `macro-flow.md`：范围、概述、分层树、阶段说明、关键交接、不变量、未知和追溯。
- `macro-flow.contract.json`：版本化机器契约。

时序图只在异步、跨系统、人工参与、回调或补偿顺序仅靠树难以理解时生成。多轮正式评审需要独立审计轨迹时才增加 `decision-log.md`；普通决定直接保存在契约中。

报告较多时，可将互不重叠的“单 Flow Pack 宏观卡片提取”委派；主分析者保留 brief、关系裁决、全局编号和冻结权。协作收益不明显时保持单分析者。

冻结前从本 skill 目录运行：

`python3 scripts/macro_flow_audit.py <contract.json> --report <macro-flow.md> --require-frozen`
