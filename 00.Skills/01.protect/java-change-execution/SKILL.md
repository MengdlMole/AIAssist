# Java 变更实施与验证

## 启动条件

开始前确认：

- 用户要求修改代码，而不只是分析或规划。
- 存在与用户目标一致且无阻塞的局部方案，或状态为 `approved` 的 `change-plan.contract.json`；只有项目规范、用户要求或高风险决定需要时才增加单独审批。
- 目标代码基线与方案证据一致；阻塞未知、冲突和必要决定为零。
- 改动范围、可观察验收结果和验证方式明确。

若方案要求 OpenSpec 或项目存在强制规范，先确认相应文档已按项目规则通过校验。不要把 OpenSpec 当作所有 Java 修改的默认前置条件。

## 实施

1. 检查工作区已有修改和仓库规范，区分用户改动与本次范围。
2. 按依赖顺序实现权威来源、查询或上游响应、承载类型、转换赋值、契约边界和最终序列化/副作用。
3. 遵循项目现有的构建、Lombok、builder、MapStruct、assembler、ORM、迁移和序列化模式；不为统一风格改动无关代码。
4. 每完成一条链路，反向核对最终结果能回到权威来源或目标状态条件，避免只修改 DTO、接口或单个中间层。
5. 如果发现证据过期、设计错误或实质性扩围，停止受影响部分并返回方案阶段；已完成且仍然有效的独立改动可以保留。

## 验证

根据风险执行适用检查，不机械运行无关的全仓库任务：

- 格式化、静态检查和编译。
- 与改动直接相关的现有单元、集成或契约测试。
- 新行为缺少保护且项目已有对应测试模式时，补充聚焦测试。
- 对关键字段或状态使用可识别值核对；纯透传检查逐层相等，存在业务转换时检查定义的转换关系和最终验收结果。
- 验证适用的正常、空值/default、异常、权限、兼容、事务、幂等和性能风险。

不能安全启动依赖真实外部系统的应用。环境不足时报告未执行项、影响和可重复的人工验证步骤，不用推测结果补齐验证。

## 交付

先复核实际 diff 没有遗漏已批准改动或混入无关修改，再报告修改文件、目标行为、关键传递链路、执行过的命令与结果、未验证项和残余风险。只有适用的编译与相关测试成功、关键链路核对通过时，才能称实现已验证完成。
