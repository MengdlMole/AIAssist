# Java 变更交付工作流

## 目标

把专项 skill 连接成一条有明确输入、输出和返工路径的交付链。只执行用户目标所需的阶段，不为了流程完整而制造文档、审批或重复分析。

当请求跨越两个以上阶段、需要落盘交接或恢复既有任务时，完整读取 [references/artifact-handoffs.md](references/artifact-handoffs.md)。

## 路由

先做轻量影响扫描，再判断请求类型；只有入口、终点或目标结果存在多个实质不同解释时才询问用户。路线由协同复杂度决定，不由文件、代码层或服务数量机械决定。

- **只读理解或故障定位**：使用 `java-code-flow-analysis`，到用户要求的终点停止。
- **单流程局部变更**：对受影响链路做必要深度的代码分析，形成聚焦方案后使用 `java-change-execution`。不强制生成宏观流程。
- **跨入口、模块或系统的业务全景**：先为缺失或过期的子流程生成 Flow Pack，再使用 `java-business-flow-synthesis`。
- **跨流程业务改造**：当变更会改变多个业务阶段/交接，或共享 API、事件、数据、状态需要多生产者/消费者协调、兼容窗口或发布顺序时，确保宏观契约已冻结且 Flow Pack 基线有效，再使用 `java-business-change-planning`；方案批准后使用 `java-change-execution`。
- **新增或透传返回字段**：同时加载 `java-add-return-field` 的字段专项约束，再按局部或跨流程路线执行。

用户明确只要分析、规划或评审时，在对应阶段交付，不继续修改代码。

## 阶段门禁

1. **定义结果**：记录目标、可观察验收结果、非目标和约束。已有信息足够时不要重新确认。
2. **建立事实**：优先复用基线一致且覆盖足够的 Flow Pack；否则只刷新受影响入口和场景。只有后续宏观提炼、跨流程规划或跨会话复用需要时才强制生成正式 Flow Pack；单轮局部变更可以直接把代码证据写入聚焦方案。
3. **选择设计深度**：
   - 单一可独立交付路径、边界清楚且不需要多方契约裁决：形成聚焦方案，说明完整传递路径、改动点、兼容性、风险和验证；即使跨代码层或调用一个外部服务，也不自动升级。
   - 多个业务流程需要共同变化，或共享契约需要协调消费者、迁移和发布：生成并批准正式 change plan。
4. **适配项目规范**：仅当目标项目已有 OpenSpec/等价规范、用户明确要求，或仓库规则强制时创建相应文档；沿用项目模板和校验方式。项目没有该规范时，不因此阻塞普通变更。
5. **实施**：只有用户要求修改且方案不存在阻塞未知时进入 `java-change-execution`。用户对实现的授权不等于允许扩大范围。
6. **验证与交付**：验证可观察结果和关键数据链路；区分已执行、未执行和无法执行的检查。

## 评审检查点

- **设计前**：复核路线、范围和证据是否足以支撑当前设计深度。
- **实施前**：复核验收结果、契约、改动点和验证是否可互相追溯。
- **交付前**：复核实际 diff、测试结果、未验证项和残余风险，确认没有把阶段性结果包装成完成。

低风险局部变更可以合并这些检查点，不为形式增加用户确认；跨流程、高风险或存在不可逆影响时分别保留。

## 返工路径

- Flow Pack 过期或覆盖不足：局部返回 `java-code-flow-analysis`，不重做无关流程。
- 宏观阶段或交接错误：提交 revision request，返回 `java-business-flow-synthesis`；冻结新版本后再规划。
- 实施中发现方案错误或实质性扩围：停止受影响修改，更新方案；只有新增的高风险决定才需要用户确认。
- 验证失败：在已批准范围内定位并修复；若失败暴露设计错误，返回规划阶段。

## 完成判断

请求要求的最后阶段已经交付，所有产物记录了彼此一致的单仓或多仓代码基线，关键未知和未验证项已明确。未完成编译、相关测试或端到端核对时，不得宣称实现已验证完成。
