# Java 新增返回字段

严格依次执行以下阶段。未满足当前门禁时停止，不得提前分析或实现。

## 通用规则

- 使用中文与用户沟通，遵循目标项目既有约束与代码风格。
- 每条消息最多提出一个问题；提问后等待用户回答。
- 不重复询问已有答案。存在影响正确性的未知项时优先询问，不得自行推测。
- 区分“代码已证实”“用户已确认”和“待确认”。
- 保留用户已有修改，不处理无关问题。
- 不以仅修改 DTO/VO 作为完成标准；证明字段从权威来源传递到最终响应。

## 1. 收集信息

详细分析代码前，只需逐个确认能启动分析的最低信息：

1. 目标项目或代码目录。
2. 目标接口、类、方法或 URL。
3. 新增字段及业务目标。

用户已提供上述信息时立即进入分析，不要在分析前追问可从代码发现的类型、层级、来源或构建方式。只询问当前最关键且无法由已有答案确定的问题。

## 2. 分析代码

信息齐全后执行只读分析：

1. 读取目标项目的 `AGENTS.md`、开发规范并检查工作区改动。
2. 使用 `rg` 定位入口、返回类型、实现类和实际执行分支。
3. 同时追踪调用方向与返回方向，包括适用的数据库/SQL、Mapper/MyBatis XML、Entity/DO、DTO/VO、converter/assembler、RPC/HTTP DTO、赋值与序列化节点。
4. 检查继承、泛型、集合、分支、批量、缓存、异步、降级、权限、异常和兼容性；避免引入 N+1。
5. 读取相似字段的真实实现，判断哪些节点可复用；字段名相似不能作为链路证据。
6. 找出首次断点，证明目标值如何从权威来源到达最终 JSON 或方法返回值。

分析后，只对代码无法证明且会影响方案的字段语义、类型、响应层级、权威来源、空值/默认值、权限、参考实现或验证要求逐个询问。发现此类未决项时停止当前阶段，不得自行假设。

## 3. 确认方案

向用户提供有代码证据的方案，至少包含：

- 目标方法、响应层级与字段契约。
- 字段权威来源、当前完整链路和首次断点。
- 逐文件修改点及修改后的完整传递路径。
- 空值、异常、权限、性能和兼容性处理。
- 测试、编译及调试计划。
- 待确认项；存在阻断项时不得给出可实施结论。

一次只询问用户是否确认该方案。用户明确确认前，不得生成 OpenSpec 文档或修改业务代码。

## 4. 生成并确认 OpenSpec 文档

方案确认后：

1. 查找目标项目中的 OpenSpec 目录、配置、说明、模板及已有变更样例。
2. 严格沿用目标项目现有规范，创建或更新其要求的 proposal、design、spec、tasks 等文件。
3. 若规范不存在、冲突或无法判断，停止并逐个询问用户；不得套用 skill 自带或臆造的模板。
4. 检查需求、设计、任务、测试与验收标准可互相追溯。
5. 运行目标项目已有的 OpenSpec validate、lint 或等价校验；未找到校验方式时逐个询问用户，校验失败时先修正文档。
6. 向用户报告文档路径、摘要和校验结果，一次只询问是否确认文档。

用户明确确认 OpenSpec 文档前，不得修改业务代码。

## 5. 实现

1. 仅实施已确认 OpenSpec 范围内的改动。
2. 按依赖顺序贯通权威来源、查询或上游响应、承载类型、转换赋值和最终序列化。
3. 遵循项目现有 Lombok、builder、MapStruct、assembler、MyBatis、迁移及序列化模式。
4. 若发现设计错误、证据失效或范围扩大，立即停止相关实现。实质性方案变化必须重新确认方案，再更新并重新确认 OpenSpec；仅文档细节变化时更新并重新确认 OpenSpec。

## 6. 测试与验证

输出测试方案和逐条测试用例，包含前置条件、数据、步骤与预期结果，覆盖适用的正常值、空值/默认值、异常、权限及兼容性场景；不适用项说明理由。

执行目标项目适用的格式化、静态检查、编译和已有相关测试。调试通过至少需要编译成功、相关现有测试成功，并使用可识别的来源值完成一条可重复的完整链路核对：

`权威来源值 == 各层传递值 == 最终响应值`

同时验证字段的响应层级、名称、类型、空值行为和序列化结果。无法启动依赖环境或执行必要检查时，说明原因、影响及人工验证步骤，并标记“未完成调试验证”。

## 7. 交付

报告 OpenSpec 文档、修改文件、完整字段链路、测试方案与用例、实际执行命令和结果、未验证项及残余风险。只有链路完整且编译调试通过，才能宣告完成；否则明确报告未完成项，不得弱化为成功。
