# Java 接口或方法新增返回字段

## 核心约束

按“定位目标 -> 确认响应契约 -> 追踪来源 -> 形成设计 -> 评审设计 -> SDD 实现 -> 端到端验证”的顺序执行。

- 始终使用中文与用户沟通，代码及项目术语遵循仓库现有风格。
- 不要把“在 DTO/VO 增加属性”当作任务完成。必须证明字段从来源到最终序列化响应的链路完整。
- 用户已提供的信息不要重复询问；先通过代码搜索补齐可发现的信息，只询问无法从仓库确认或涉及业务决策的内容。
- 每个确认阶段一次只集中询问当前阶段的必要问题，避免一次抛出整套问卷。
- 缺少会影响正确性的业务信息时停止设计或实现，不要自行猜测。
- 区分“代码已证实”“用户已确认”“待确认”和“假设”；设计与评审结论必须引用具体文件、类、方法或 SQL 作为证据。
- 未完成设计评审前不要修改业务代码；用户明确要求只分析或只出设计时，不进入实现。
- 保留用户已有改动，不处理与本任务无关的问题。

## 阶段零：读取项目约束

1. 查找并读取目标仓库中的 `AGENTS.md`、开发规范、接口规范及现有 SDD/spec/design 模板。
2. 检查工作区状态，识别用户已有改动；存在重叠修改时先理解并保留，无法安全合并时再询问用户。
3. 使用 `rg` 优先搜索代码。先收集证据，再提出仓库无法回答的问题。
4. 建立待确认清单，后续每完成一个阶段就更新；未决项会改变方案、响应契约或数据正确性时，不得越过对应门禁。

## 阶段一：定位目标方法

1. 询问需要在哪个接口或方法新增字段返回，并要求提供能唯一定位目标的线索，例如 URL、类名、方法名或业务描述。
2. 使用 `rg` 搜索 URL、方法名、Controller 映射、接口声明和实现类。读取实际代码，不仅依赖用户口述。
3. 从入口方法确认直接返回类型，并递归展开通用响应包装、泛型、集合元素和嵌套 DTO/VO，定位字段最终所属的返回模型。
4. 扫描返回模型及其构造路径，包括：
   - 字段、继承关系、泛型和嵌套层级；
   - getter/setter、构造器、builder、Lombok；
   - Jackson/Fastjson 等序列化注解；
   - converter、assembler、MapStruct、BeanUtils 或手工赋值；
   - 多态响应、接口/抽象父类、分页包装和条件分支使用的不同实现类型；
   - 相同或相似字段在项目中的现有实现。
5. 同时检查 OpenAPI/Swagger、JSON Schema 或项目内接口文档，确认是否需要同步响应契约。
6. 向用户报告并确认定位结果：入口文件与方法、返回模型文件、目标响应层级。存在同名方法或多个入口时，必须让用户选择后再继续。

如果当前没有可读取的项目代码，明确要求用户提供仓库、代码目录或关键代码片段，不能假装已经完成定位和扫描。

## 阶段二：确认响应字段契约

在目标位置确认后，询问并确认：

1. 字段位于响应的哪个位置或层级；列表响应要明确是列表元素字段还是分页/响应包装字段。
2. Java 字段名和对外 JSON 字段名；未特殊指定时保持项目现有命名与序列化策略。
3. Java 类型；同时确认数据库、上游接口或计算结果类型是否需要转换。
4. 访问权限，默认 `private`。
5. 必要的字段语义：是否允许 `null`、默认值、枚举含义、格式、单位、精度、时区、脱敏和权限规则。

用一段简短摘要复述响应契约并取得确认。若用户已经清楚给出这些信息，直接复述确认，不重复提问。未确认目标层级、字段名或类型时，不进入来源设计。

## 阶段三：追踪字段来源和调用链

询问字段的权威来源，例如数据库表字段、其他方法返回、RPC/HTTP 响应、缓存、配置、枚举或计算逻辑。然后以目标入口为起点分析真实代码链路：

1. 追踪 Controller/API -> application/service/domain -> repository/mapper/DAO -> MyBatis XML/数据库，或追踪到内部方法、RPC/HTTP client。
2. 同时追踪返回方向的对象转换、组装与赋值，不只追踪调用方向。
3. 搜索字段名、数据库列名、上游 DTO 字段名和语义相近字段，记录每一跳的文件、方法、承载类型及赋值方式。
4. 检查分支、批量路径、异步路径、缓存路径、降级逻辑和不同实现类，确认目标请求实际经过哪条路径。
5. 基于代码证据判断来源是否已在现有流程中：
   - **已有流程**：当前调用链已经查询或获取该值，只是某一层未承载、未转换或未返回。
   - **可扩展的已有流程**：当前调用链已到达权威来源，但现有查询或上游响应尚未包含该值。
   - **无已有流程**：当前调用链无法到达该来源，需要新增查询、调用或计算流程。

不要因项目中存在同名字段就判定为已有流程；必须证明它位于目标方法实际执行的数据链路上。向用户说明字段来源和判定结果；来源描述有歧义时先请用户确认。

将证据整理成链路表，至少包含“顺序、调用/返回节点、文件与符号、输入、输出、字段是否已承载、证据状态”。调用方向和返回方向都必须能连通；只有类名或字段名相似不能作为连通证据。

## 阶段四：设计数据传递链路

### 已有流程或可扩展流程

分析最小且完整的改动：

- **数据库来源**：先确认表中是否已有目标列。若已有，检查 DO/entity、mapper、查询列、SQL 片段、别名、`resultMap`、类型处理器、转换器和 VO 赋值；若不存在，只有在该表确为权威来源时才设计 DDL/迁移，并继续追踪新列的写入/同步来源、历史数据回填、发布顺序与回滚方案，避免只读不写。
- **MyBatis XML**：检查显式列清单、复用 `<sql>`、`resultMap`、构造器映射和多表同名列。列名与 Java 字段名不一致时使用项目既有的别名或显式映射方式，并评估复用 SQL 对其他查询的影响。
- **内部方法来源**：确认被调用方法的返回类型是否承载该值；若没有，继续向下追踪，不能在中间层伪造数据。
- **外部接口来源**：检查对方契约、client response DTO、反序列化字段名、版本兼容、超时/失败降级和空值行为。不能假定上游已经返回该字段。
- **计算来源**：确认所有输入已存在，明确计算规则、精度和空值处理，避免重复查询。
- **列表或批量接口**：优先扩展批量查询或批量调用，检查关联键和回填映射，禁止无评估地引入 N+1。

### 无已有流程

先询问用户希望在哪里添加获取流程，并确认以下业务决策后再设计：

- 新流程所在层级和获取方式：扩展 SQL、新增 SQL、内部方法、外部接口、缓存、配置或计算。
- 查询/调用入参、关联 ID 或业务键，以及一对一、一对多或缺失数据的处理。
- 单条与批量策略、缓存和性能要求、事务与一致性要求。
- 超时、异常、权限不足和来源无值时的返回行为。
- 数据权限、租户隔离、脱敏、接口版本和向后兼容要求。

如果用户指定的新增位置破坏现有分层或会产生明显性能/一致性问题，说明风险并给出符合项目现有模式的替代方案，待确认后继续。

## 阶段五：生成设计文档

实现前生成设计文档。优先遵循仓库已有的 SDD、spec、design 或 docs 目录及模板；没有约定时，读取并使用 [references/design-template.md](references/design-template.md)，将文档写入仓库内合适的 `docs/` 目录。若用户只允许在对话中输出，则在对话中提供完整设计。

设计文档至少包含：

1. **需求与范围**：目标入口、响应层级、字段契约、字段来源、包含与不包含的范围。
2. **现状分析**：实际调用链、返回组装链、关键文件/方法、来源是否在现有流程及判断证据。
3. **方案设计**：方案选择、逐文件修改点、接口/模型/SQL/上游契约变化。
4. **数据链路**：用箭头和链路表列出每一跳，例如 `table.column -> DO.field -> Mapper result -> Service DTO -> ResponseVO.field -> JSON field`，并附代码证据。
5. **赋值规则**：映射、类型转换、默认值、空值、格式化、枚举、权限和异常处理。
6. **数据库或外部依赖**：DDL/回填/回滚、MyBatis 映射，或外部契约与降级策略；不适用时明确写明。
7. **兼容性与风险**：N+1、查询范围、序列化、缓存、权限、历史数据、调用方影响。
8. **验收标准与测试**：可观察的最终响应、单元/集成/接口测试、空值及异常场景。
9. **实施顺序**：按依赖关系排列的小步任务，使每项修改能对应到设计和验收标准。
10. **待确认项与证据**：记录尚未证实的外部事实、负责人及其对实现的阻断程度；不要把假设写成结论。

## 阶段六：评审设计

在实现前对设计文档做一次显式 review，并输出结论。逐项检查：

- 目标请求确实经过文档所列调用链，最终 JSON 能出现正确层级、名称和类型的字段。
- 来源权威且可获得；数据库列或上游字段是否存在已有证据，待外部确认项是否明确标注。
- 每一跳都有承载字段、映射或赋值动作，没有 entity/DO、DTO、converter、MapStruct、builder、分页元素等断点。
- MyBatis 查询列、别名、`resultMap`、类型处理和 Java 字段完全匹配，写入来源及历史数据问题已覆盖。
- 批量接口没有 N+1，关联键、重复键和缺失值处理正确。
- 空值、默认值、类型转换、权限、租户、脱敏、序列化和兼容性行为明确。
- 测试能够从可控来源值验证最终响应值，而不只是检查模型存在字段。
- 修改清单与数据链路逐项对应，没有遗漏必要文件，也没有无依据的额外改动。
- 需求、设计修改点、测试与验收标准能够互相追溯；每个新增字段的每一跳都有唯一、明确的赋值来源。

Review 结果只能是“通过”或“需修订”。发现断链或未决业务问题时，修订设计并重新 review；需要用户决策时先询问。设计通过后向用户报告结论，再进入实现。

## 阶段七：按 SDD 实现

优先采用项目已有 SDD 流程。若仓库没有明确约定，按以下默认流程执行：

1. 将已通过 review 的设计文档作为规格基线，把验收标准转换为测试场景或可执行检查。
2. 优先补充或更新能暴露缺失字段/错误映射的测试；无法先写自动化测试时，记录原因并定义可重复的接口验证。
3. 按设计中的实施顺序小步修改，通常从权威数据来源向最终响应推进；每完成一跳就核对承载、映射和赋值。
4. 只实施设计范围内的改动。实现发现设计错误、证据失效或新增范围时，立即停止相关实现，先更新文档并重新 review，保持规格与代码一致。
5. 遵循项目现有 Lombok、builder、MapStruct、assembler、MyBatis XML、迁移工具和测试风格。
6. 运行格式化、编译、相关单元/集成/接口测试。检查 MyBatis XML 可加载，必要时验证实际序列化 JSON 和 SQL 映射。
7. 根据验收标准执行端到端核对，使用一个可识别的来源值证明“来源值 == 各层传递值 == 最终响应值”，并验证字段所在 JSON 层级、名称、类型、空值/默认值和权限行为。
8. 最终交付说明设计文档、修改文件、完整数据链路、测试结果，以及无法验证的外部依赖或残余风险。

## 完成标准

只有同时满足以下条件才宣布完成：

- 目标方法和最终返回模型已经确认。
- 字段契约和权威来源已经确认。
- 设计文档已生成并通过 review。
- 实现与设计一致，字段传递和赋值链路无断点。
- 相关测试或可重复验证已执行，最终响应中的字段名称、层级、类型和值正确。
